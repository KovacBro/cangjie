## 0. 摘要（先看这段）

仓颉不是"文本压缩工具"，是一套**长任务上下文治理方案**。它由三件事组成：

| 层 | 组件 | 作用 | 是否无损 |
|---|---|---|---|
| L0 | `Codec` 字码编解码 | 高频短语 ⇄ 单字，逐字节可逆 | 无损 |
| L1 | `mine` 挖掘器 | 从语料里找出"值得造字"的短语 | — |
| L2 | `pack` 工作记忆包 | 把项目状态压进固定 token 预算 | 有损（可回溯原文） |

真正让"项目后期不越来越贵"的是 **L2 的定长预算 + L1 的字典复用**，L0 只是让同一份记忆更便宜。
只做 L0（把短语换成字）而不做 L2，收益上限只有几个百分点——这是实测结论，第 8 章有数据。

## 1. 缘起与目标

### 1.1 问题

长任务（跨几十轮的重构、写书、造世界、持续排障）的 token 花销不是线性增长，是**平方增长**：

```
第 t 轮的输入 ≈ 系统提示 + 历史(t-1 轮的全部内容) + 本轮输入
累计成本  ≈ Σ_{t=1..n} (t × 每轮新增)  = O(n²)
```

于是"任务越繁复 → 上下文越长 → 每轮越贵 → 越容易超窗 / 被截断 / 变笨"。

### 1.2 目标（可验收）

1. **压缩**：高频短语折叠成单字，单次压缩率 ≥ 3%（中文文档语料），且**完全可逆**；
2. **不膨胀**：字典规模有硬上限，字典本身注入成本有上界，项目后期总成本趋近常数；
3. **多语言**：中文、英文、中英混排、代码注释同一套机制，不依赖分词词典；
4. **可读**：压缩后的字**在终端/聊天/编辑器里能正常显示**，不是乱码；
5. **可回退**：任何对外输出都能一键还原成人类原文，**绝不把字码泄露给用户**。

### 1.3 非目标

- 不做通用压缩（zip/BPE 训练那种）；
- 不替代 prompt caching / RAG；
- 不承诺"压缩后模型推理质量不降"——第 9 章有专门讨论。

## 2. 设计原则

| # | 原则 | 解释 |
|---|---|---|
| P1 | **先量后造** | 载体字必须先实测 token 单价再选；不许凭直觉用"生僻字"（实测更贵，见 3.2） |
| P2 | **账要算清** | 字典条目本身要花 token，必须"挣回成本"才收录（`amortization`） |
| P3 | **宁缺勿滥** | 配不上便宜载体的短语一律丢弃；字典越短越值钱 |
| P4 | **无损优先** | 编码必须逐字节可逆，代码块/路径/URL 默认不动 |
| P5 | **有界** | 字典条数、包体积、单条短语长度都有硬上限 |
| P6 | **可解释** | 每个字都能查到"原意 / 义符 / 单价 / 命中次数 / 净收益" |
| P7 | **失效安全** | 任何环节缺席（无 tiktoken / 无字体 / 无网络）都必须优雅降级 |

## 3. 关键实测：什么字才真的便宜

> 这一章推翻了本项目最初的设计。原始方案用「CJK 扩展 A 区生僻字」当载体（看起来最像"造出来的字"），
> 实测后**全部作废**——因为它们在真实分词器里要 3 个 token，比被压缩的短语还贵。

### 3.1 实测方法

```bash
cangjie bench                    # 打印当前分词器下各载体族的实测单价
cangjie calibrate                # 逐字实测 BMP 全区间，产出 assets/carriers-<encoding>.json
```

对 BMP 全部 65536 个码位逐个 `encode()`，记录单价（`o200k_base`，2026-10 实测）。

### 3.2 实测结论（o200k_base）

| 字符族 | 单 token 占比 | 备注 |
|---|---|---|
| CJK 扩展 A（U+3400 起） | **0.0%** | 96% 是 3 token——最差选择 |
| 私有区 PUA（U+E000 起） | 0.0% | 平均 2.38 token |
| 常用汉字（U+4E00 起 3000 字） | 19.5% | **80% 是 2 token** |
| 几何图形（■□▲△◆◇） | 17.7% | ✅ 便宜 |
| 数学符号、箭头 | 4.3% / 4.5% | ✅ 少数可用 |
| 希腊字母、西里尔字母 | 高 | ✅ 可用 |
| 拉丁扩展（ÀÁÂÃÄÅ…） | 高 | ✅ 可用 |
| 制表符 / 装饰符号 | 8% / 3% | 一般 |

常用词单价（同一分词器）：

```
数据库=1  连接池=2  数据库连接=2  向量检索=4  重排序=2  超时=2  文档解析=3
```

**结论**：中文在 o200k 里已经压到约 0.6 token/字，所以
> 只有单价 ≥ 3 token 的短语才值得造字，且载体必须是 **1 token** 的字符。

### 3.3 载体的三档预设

| 预设 | 取字顺序 | 适用 |
|---|---|---|
| `auto`（默认） | 几何→数学→箭头→记号→希腊→西里尔→注音→拉丁扩展→汉字 | 最低价优先 |
| `sym` | 同上，纯符号族 | 视觉上明确"这是编码" |
| `han` | 汉字优先 | 看着最像"真字"，形义相合 |
| `forge` | 私有区自造字 | 需要装字体，形态独一无二 |

全局可用单 token 字符：**5211 个**（BMP 普查，已随包附带 `assets/carriers-o200k.json`）。
按单价分层后：1 tok × 2843、2 tok × 19847、3 tok × 13182。

## 5. 数据模型

### 5.1 `.cangjie/` 目录

```
.cangjie/
├── config.json     # 配置（阈值、上限、载体预设）
├── dict.json       # 字表（唯一的真实来源）
├── ledger.jsonl    # 追加式账本（每次压缩/入库/裁剪一条）
├── digest.txt      # 全语料压缩摘要
└── pack.md         # 预算内工作记忆包
```

### 5.2 `dict.json`

```json
{
  "version": 1,
  "pool": "auto",
  "count": 2,
  "entries": [
    {
      "g": "▀",              // 载体字（单字符）
      "p": "向量检索",        // 原短语
      "n": 12,               // 语料中出现次数
      "cls": "事",           // 义符（语义类）
      "cost": 4.0,           // 原短语 token 单价（实测）
      "gcost": 1.0,          // 载体字 token 单价（实测）
      "hits": 48,            // 实际压缩命中次数
      "created": "2026-10-27T20:40:00",
      "last_used": "2026-10-27T20:52:11",
      "note": ""
    }
  ]
}
```

派生指标：

```
saved_per_hit = max(0, cost - gcost)          # 每次命中省多少
entry_cost    = cost + 4                      # 字典条目注入成本（字+分隔符+原文+换行）
net           = hits × saved_per_hit - entry_cost
density       = net / entry_cost              # 淘汰排序用
```

### 5.3 账本 `ledger.jsonl`

一行一个事件，永不改写：

```json
{"ts":"...","event":"compress","chars":1203,"hits":17,"tokens_before":812.0,"tokens_after":655.0}
{"ts":"...","event":"mine","added":32,"entries":32}
{"ts":"...","event":"prune","dropped":8}
```

有了账本，`stats` / `report` 才能给出**实测**（而不是估算）的节省数字。

## 6. 协议（核心，必须严格遵守）

### 6.1 密码本格式（注入上下文用）

```
<仓颉v1 pool=auto n=12>
▀=向量检索
▄=重排序
█=数据库连接池
</仓颉>
```

- 首行 `<仓颉v1 ...>` 必须原样保留：版本号防止新旧表混用，`n` 用于自校验；
- 每行 `字=原意`，`=` 为唯一分隔符（短语内不会出现 `=`，入库前做校验）；
- 整块**必须一次性、逐字节稳定**地出现在提示词同一位置（见 10.3 prompt caching）；
- 结尾 `</仓颉>` 后空一行再接正文。

### 6.2 编码规则

| 规则 | 说明 |
|---|---|
| R1 最长优先 | 同一位置多个短语可匹配时取最长（`Codec._match` 走 trie） |
| R2 保护区 | 围栏代码块 ```` ``` ````、行内代码 `` ` ` ``、URL、`C:\路径`、`./路径` 默认**不压缩** |
| R3 字面转义 | 原文若恰好含载体字，编码为 `\X`；解码时 `\X` → 字面 `X`，`\\X` → `\` + 字面 `X` |
| R4 反斜杠不动 | 普通 `\` 不参与转义，因此 `C:\Users` 解码后原样保留 |
| R5 只减不增 | 编码器绝不替换"压缩后更长"的短语（收益为负的已在上游被滤掉） |
| R6 幂等 | `decode(encode(x)) == x`，对任意 UTF-8 文本成立（`doctor` 每次自检） |

### 6.3 输出闸门（铁律）

> **字码只活在"内部世界"：思考、草稿、工具输出、工作记忆包。
> 一旦要给用户看，必须先 `cangjie expand`。**

| 场景 | 允许出现字码？ |
|---|---|
| 内部推理、临时笔记 | ✅ |
| 喂回模型的历史摘要 | ✅ |
| 给用户的最终回答 | ❌ 必须还原 |
| 交付的文件（代码/文档/配置） | ❌ 必须还原 |
| git commit / PR 描述 | ❌ 必须还原 |
| 终端里给人看的命令输出 | ⚠️ 可保留，但需附 `cangjie expand` 提示 |

违反后果：用户看到一屏"▀▄█"会认为模型坏掉了——**这比省下的 token 贵得多**。

### 6.4 保护区为什么默认开

代码块里的标识符若被换掉，会产出"看起来对、实际跑不了"的代码。仓颉宁可牺牲压缩率：
受保护片段在 `CodecStats.protected_chars` 里单独计数，可量化"有多少内容注定压不了"。

## 7. 算法

### 7.1 切分

- **词元**（unit）：CJK 单字 = 1 个词元；`[A-Za-z][\w'\-]*` = 1 个词元；数字 = 1 个词元；
- **句子边界**：`。！？；!?;，,\n` 任一处断开，n-gram 不跨句；
- **窗口**：中文 2–10 词元，英文 2–4 词元，短语字符数 ≤ 28。

### 7.2 三重过滤（新词发现）

只数 n-gram 会挖出"果的重排序模型用"这种从词中间切开的碎片。三道闸：

**① 频次** `count ≥ min_freq(3)`，且 `df ≥ 2`（文档 ≥3 篇时）。

**② 自由度**（左右邻接熵）

```
H_left(p)  = -Σ_x  P(x|left) log2 P(x|left)
freedom(p) = min(H_left, H_right)  ≥ min_freedom(0.9 bit)
```

碎片有一个固定邻居（`果` 永远跟在 `结` 后面），熵趋近 0；真词两侧自由组合。

**③ 凝聚度**（PMI 比值化）

```
cohesion(p) = min over 切分点  count(p) × N / (count(left) × count(right))   ≥ min_cohesion(2.0)
```

切分点取**词元边界**（不是字符边界），否则英文会被从单词中间切开。

**④ 形态过滤** `fragmentish()`：以虚词开头/结尾（的、了、而、就以…）、含数字（跨文档不稳定）、空格过多 → 丢弃。
这条刻意收窄（只放极不可能成词的虚词），宁可漏杀不可错杀——`向量`、`在线`、`存在` 都是真词。

**⑤ 极大化**：若存在更长且频次 ≥ 0.6× 的短语包含当前短语，说明当前这条是被截断的碎片 → 丢弃。

### 7.3 token 收益模型

```
effective  = prose_count + (code_count) × 0.25      # 只出现在代码区的短语打折
gross      = effective × (cost(phrase) - gcost)      # 毛收益（每命中省多少）
entry_cost = cost(phrase) + 4                        # 字典条目成本
net        = gross - entry_cost × amortization        # → 必须 > 0 才收录
```

`amortization` 默认 1.0——即"这条字典必须在本次语料周期里自己挣回自己"。

### 7.4 载体选型（本项目最有价值的一段）

不是"每条短语配一个字"，而是**按短语价值配多贵的字**：

```
候选按 net 降序 → 对每条取队首（最便宜且未占用）载体：
    若  cost(phrase) - cost(glyph) >= min_gain(1.5)  →  占用该字
    否则 →  本条不压缩（放弃，不浪费载体）
```

效果：`向量检索`(4 tok) 配 1 tok 的 ▲；`node.orbitDist`(4 tok) 配 1 tok 的 ▪。
若某条短语只有 2 tok，它会**找不到合适载体而被丢弃**——这正是 3.2 结论的直接后果。

### 7.5 解码

单字符映射扫描 + 转义状态机，O(n)，对 22 万字符语料实测 < 0.2s。

## 8. 实测基准

> 全部在本机实测，分词器 `o200k_base`，语料为真实工程文档。
> 复现：`python tests/bench.py`（见 `tests/`）。

### 8.1 中文技术文档（真实工程 `盘古`，26 文件 / 276,564 字符 / 116,446 token）

复现：`python tests/bench.py "E:/skills/盘古"`

| 字典上限 | 实收条目 | 压缩后 | 单次压缩率 | 字典成本 | 净省 |
|---|---|---|---|---|---|
| 32 | 32 | 115,282 | 1.0% | 224 | 940 |
| 64 | 64 | 114,304 | 1.8% | 464 | 1,678 |
| 128 | 128 | 113,244 | 2.7% | 899 | 2,303 |
| 256 | 256 | 111,976 | 3.8% | 1,762 | 2,708 |

**读 5 次**（字典只付一次）：3.5%；**读 20 次**：3.8%（趋近单次压缩率上限）。

> 另一次更"纯中文"的实验（仅 17 个 .md，75,938 字符 / 44,845 token）中，
> 128 条方案单次压缩率 **4.0%**、净省 886 tok。语料越重复，压缩率越高。

### 8.2 英文文档（prompt 类语料，200,000 字符）

条目 7 条，压缩率 0.2%。原因：英文 prompt 语料重复度低，且常用词组本来就只有 1–2 token。

### 8.3 源码（79,136 字符）

条目 22 条，压缩率 0.9%。原因：代码块在保护区内，**本来就不压**；标识符跨文件不复用。

### 8.4 怎么读这组数字（重要）

1. **单次压缩率低（1–4%）是正常的**，因为中文已高度 BPE 化，且大部分文本只出现一次；
2. **收益 = 压缩率 × 重读次数**。系统提示、项目摘要、术语表这类"每轮都读"的内容才是主战场；
3. **想要 40%+ 的节省，靠 L2 有损摘要（`pack`），不是靠字码**——字码保证的是"摘要里的专名不丢、还能还原"；
4. 任何声称"中文无损压缩能省一半 token"的说法，都是没实测过。

## 9. 增长控制：为什么后期不会越来越贵

### 9.1 三段式上下文治理

| 区 | 内容 | 预算 | 更新策略 |
|---|---|---|---|
| **Z0 当前窗口** | 最近 k 轮原始对话 + 本轮工具输出 | 固定 k | 滑动 |
| **Z1 工作记忆** | `pack.md`：密码本 + 压缩摘要 | **固定 B token（默认 2000）** | 每 5–8 轮或状态变更时重建 |
| **Z2 归档** | `digest.txt` / 原始文件 | 不占上下文 | 需要时按需检索 |

每轮提示词 = 系统 + Z1(B) + Z0(k×每轮) = **O(1)**，与任务总轮数无关。

```bash
cangjie digest              # 重建 Z2 摘要（全语料压缩）
cangjie pack --budget 2000  # 重建 Z1，超预算自动截中间、保留头尾
```

### 9.2 字典自身的封顶

- 条数 ≤ `max_entries`（默认 128）→ 注入成本 ≤ 128 × (均价+4) ≈ 900 tok；
- 超限按 `density = net / entry_cost` 淘汰；
- 整体 ROI < 1 时 `audit` 主动劝你缩表；
- 净收益为负的条目（`net ≤ 0 且 hits > 0`）自动判死。

**结果**：字典成本是常数上界，摘要成本是常数上界，历史成本是窗口常数 → 总成本常数。✅

### 9.3 增长模型（`budget.simulate`）

30 轮、每轮新增 1200 tok、字典 300 tok、压缩率 0.55：

```
不压缩累计 558,000 tok     仓颉累计 305,850 tok     省 45%
每轮成本曲线 不压缩 ▁▁▂▂▃▄▄▅▆▇██    仓颉 ▁▁▁▂▂▂▃▃▄▄▄▅

## 10. 造字（可选增强）

### 10.1 造字规则

合体字 = **左义符 + 右声符**（形声字结构）：

| 义符 | 语义场 | 例 |
|---|---|---|
| 数 | 数据/指标/token | 数据库指标 |
| 错 | 错误/异常/调试 | 超时重试 |
| 器 | 组件/框架/工具 | 渲染引擎 |
| 文 | 文件/文档/路径 | 配置文件路径 |
| 事 | 任务/流程（兜底） | 工作记忆包 |

声符取短语首个有意义字符。`spec_for()` 产出 `GlyphSpec(glyph, phrase, cls, phon, layout)`。

### 10.2 两种落地方式

| 方式 | 产物 | 优点 | 缺点 |
|---|---|---|---|
| SVG 图样 | `assets/glyphs-preview.html` | 零依赖、任何设备可看 | 只是"画出来的字"，不能输入 |
| TTF 字体 | `assets/CangjieCompress.ttf`（PUA U+E000 起） | 真字符、可输入、可搜索 | 需装字体；**单价 2–3 tok，不划算** |

```bash
cangjie forge            # 生成 TTF + 预览页（需 fonttools + 系统 CJK 字体）
```

实测生成的字体：upem 2048，5 个字形轮廓正常，`getBestCmap()` 映射 U+E000–U+E004。

### 10.3 为什么造字默认不用

按 3.2 的实测，PUA 载体均价 2.38 tok，比 1 tok 的几何符号贵一倍多。
**造字的价值是"形态识别"和"身份感"，不是省 token。** 默认关闭，`--pool forge` 才启用。

## 11. 失效模式与边界（诚实清单）

| # | 风险 | 触发条件 | 缓解 |
|---|---|---|---|
| 1 | 模型误解码 | 字表更新后仍用旧表 | `<仓颉v1>` 版本头；表与包同生同灭 |
| 2 | 码表漂移 | 两次 mine 产生不同分配 | 已入库短语永不重新分配；`g` 只增不改 |
| 3 | 分词器差异 | 换模型（cl100k↔o200k↔Claude） | `calibrate` 重新普查；`carriers-<encoding>.json` 分文件 |
| 4 | 字体缺字 | 用了 Ext-A/PUA 又没装字体 | 默认 `auto` 只用 BMP 常用区 |
| 5 | 代码被改坏 | 关掉 `protect_code` | 默认开；文档红线标注 |
| 6 | 用户看到字码 | 忘了 expand | 输出闸门铁律（6.3） |
| 7 | 压缩反而更贵 | 短语太短 / 重读太少 | 收益模型 + `amortization` + ROI 审计 |
| 8 | 破坏 prompt caching | 每轮重建包导致前缀变化 | 见 12.3 |
| 9 | 推理质量下降 | 过度压缩致使语义模糊 | 只压"命名实体"，不压"逻辑连接词"；`min_gain` 已拦掉短词 |
| 10 | 离线环境 | 无法下载 BPE | tiktoken 探测超时 2.5s 后永久降级到启发式 |

## 12. 与其它机制的关系（先进经验）

### 12.1 vs BPE / 分词器

分词器已经在做"子词压缩"，仓颉做的是**"跨子词短语"压缩**——这是 BPE 的空白区
（BPE 有 `数据库` 的合并，但没有 `数据库连接池` 的合并）。

### 12.2 vs RAG

RAG 解决"找不到"，仓颉解决"放不下"。二者正交：检索回来的片段也可以用仓颉压一遍再入上下文。

### 12.3 vs Prompt Caching（**最容易踩的坑**）

多数厂商的 prefix cache 要求**前缀逐字节一致**。如果你每轮都重建 `pack.md`，
前缀就变了，缓存全失效，**省下的 token 反而赔在缓存未命中上**。

正确做法：

1. 密码本块放在最前，且内容稳定（只增不改，追加新条目放末尾）；
2. `pack.md` 重建频率 ≤ 每 5–8 轮一次，而不是每轮；
3. 若 provider 有缓存，优先"稳定前缀 + 尾部追加"，让压缩块成为缓存命中区；
4. 量化对比：`(省下的 token) × 单价` vs `(缓存未命中的 token) × 差价`。

### 12.4 vs KV cache / 更长的上下文窗口

窗口变长不等于便宜。窗口只是"装得下"，成本还是按 token 算。仓颉治的是成本，不是容量。

## 17. 裁剪与记忆层：把"最省的那几刀"补完

字码只解决无损打底（1–4%）。真正降账单的是另外三件：**裁剪、状态卡、定长包**；
同时去掉宿主绑定。

### 17.1 量级对照（先看这个）

| 手段 | 典型节省 | 性质 | 模块 |
|---|---|---|---|
| 输出裁剪 `trim` | **70–95%** | 有损 | `cangjie/trim.py` |
| 状态卡 `state` | 该段历史 **90%+** | 有损（结构化） | `cangjie/memory.py` |
| 定长包 `pack` | O(n²) → O(1) | 有损（可回溯） | `cangjie/memory.py` |
| 字码 `codec` | 1–4% | **无损** | `cangjie/codec.py` |

结论写进 SKILL.md 的第一屏：**只做字码不做裁剪，等于白干。**

### 17.2 trim：按优先级裁剪，而不是按位置截断

```
优先级 3：错误行及其上下文（前后 error_context 行）
优先级 2：尾部（结论、汇总、退场信息）
优先级 1：头部（命令、起点）
超行数上限时 → 先牺牲优先级 1，绝不牺牲错误行
```

三道辅助规则：

1. **噪音先行**：`NOISE` 正则先滤掉进度行（`... PASSED [ 30%]`、`Downloading…`、纯符号行），
   否则几百行通过用例会全部获得最高优先级，把真正的失败行挤掉（v1.0 后期踩过的坑）；
2. **重复折叠**：连续 ≥3 行相同 → `line  (×N)`；
3. **缺口标注**：不连续处输出 `……[省略 N 行]……`，保留"哪里被跳过"的信息。

实测：408 行合成 pytest 输出 → 26 行，29318→1607 字符（**-94.5%**），
`FAILED` / `short test summary` / `Traceback` / `AssertionError` 全部保留。

剖面（profile）：`pytest` `jest` `npm` `git-diff` `docker` `ls` `build` `generic`，
由 `detect_profile(cmd)` 自动识别。

### 17.3 memory：三段式，把成本钉成常数

```
state.json   目标 / 阻塞 / 已决 / 下一步 / 事实   —— 实测 5 项 = 68 tok
roll.jsonl   只追加的结论行（最多 40 条，超出丢最老）
pack.md      密码本 + 状态卡 + 滚动结论 + 摘要，硬预算内
```

`build_pack()` 的预算分配：

```
block（密码本，绝不裁）→ state（≤20% 预算，超了逐行丢细节）
→ roll（吃掉剩余 70%，从最新往前取）→ digest（剩余，取尾部）
```

为什么不是"每次摘要整段对话"：那是 O(全历史) 的重写，本身就贵。
滚动追加是 O(本轮)，与轮数无关。

### 17.4 seed：人工意图优先

统计挖掘永远抓不到"只出现两次但极其关键"的项目代号。
`cangjie seed --add …` 直接写入并 `pinned=True`：**不占淘汰名额、不因净收益为负被清退、
不重新分配载体字**。

### 17.5 去宿主绑定

| 层 | 做法 |
|---|---|
| 技能层 | 只有一个 `SKILL.md`（Agent Skills 通用约定：frontmatter + 说明） |
| 命令层 | `pyproject.toml` 提供 `cangjie` console script；`scripts/cj.py` 免安装 |
| 协议层 | `mcp_server.py` 手写 JSON-RPC 2.0 over stdio，6 个工具，零依赖 |
| 文档层 | `install --target workbuddy/claude/agents/dir`，`agents` 幂等写 `AGENTS.md` |
| 数据层 | 普查表同时放在 `cangjie/data/`（随包）与 `assets/`（源码布局） |

### 17.6 验收

```bash
python tests/test_cangjie.py     # 29 项（+10）
cangjie doctor
cangjie trim -i <长日志> --profile pytest   # 应 >80%
cangjie pack --budget 700                   # 应 ≤700

```

### 17.7 仍然没做的

- 两字码（L3 层，字典容量 ×10）；
- 模型辅助的术语判定（现在纯统计，误判率约 20–30%）；
- 压缩后的**质量回归**（A/B 回放）：只能说"文本无损"，不能说"推理无损"。
