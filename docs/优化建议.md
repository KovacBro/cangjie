# 仓颉优化建议（1.0 之后的路线）

> 写给"还想再省一点"的人。按 **投入产出比** 从高到低排，每条都给判断依据。
> 先给结论：**字码不是最省 token 的手段，只是最"无损"的那一个。**

---

## 0. 结论先行：五种手段的真实量级

| 手段 | 典型节省 | 是否无损 | 状态 | 建议 |
|---|---|---|---|---|
| ① 工具输出裁剪（head/tail + 只留报错） | **70–95%** | 有损 | ✅ 已实现 `cangjie trim` | 🥇 先做这个 |
| ② 结构重排（JSON/表格 → 定长行） | **30–80%** | 基本无损 | ⬜ 未做 | 🥇 第二优先 |
| ③ 状态卡 + 滚动结论 + 定长包 | **40–70%** | 有损可回溯 | ✅ 已实现 `state/roll/pack` | 🥈 长任务必做 |
| ④ 字码短语压缩（本 skill 的 L0） | **1–4%** 单次，随重读放大 | **无损** | ✅ 已实现 | 🥉 打底 |
| ⑤ 不提（请求精简、别贴整文件） | 无上限 | — | 人力 | 永远有效 |

> 1.0.0 已落地 ①③ 与 MCP/多宿主；下表保留原始判断与未做项，供继续开发参考。

**所以：如果你只做一件事，不要做字码——去做①。**
仓颉的定位是"③的伴侣"：让摘要更短、让专名不丢、让原文可还原。

## 1. 载体层（收益确定，改动小）

### 1.1 码长-价格曲线：让载体"按需变长"

现状是"一条短语一个字"。但 128 条字典之外还有大量"次高频"短语，配不上 1 token 的字。

可以做**两字码**：`▲▲`、`▲△`…，组合数 已用字数 × 全池字数。
- 单价 2 token，能压 5 token 以上的短语（`node.orbitDist` 4 tok 就不划算，但 `数据库连接池配置` 6 tok 划算）；
- 关键是**编解码要无歧义**：两字码用"保留字首 + 索引字"结构（首字固定为 `▲`，第二字是索引），
  这样 `▲X` 永远是一个整体，不会被误拆。

预期：字典容量 ×10，整体压缩率 +1~2 个百分点。**收益不高，但成本也极低。**

### 1.2 分层码表（高频短码 + 低频长码）

```
L1（≤16 条，最热）：1 tok 单字   ← 每轮都出现
L2（≤128 条）：1 tok 单字        ← 当前实现
L3（≤1024 条）：两字码           ← 备而不用
```
只有当 L2 用尽且仍有正收益候选时才启用 L3，避免"码表变长抵消收益"。

### 1.3 按模型分别校准（必做，但用户无感）

不同模型的分词器差异极大：

| 分词器 | 常用汉字单价 | 备注 |
|---|---|---|
| `o200k_base`（GPT-4o 系） | 1–2 tok | 本 skill 的实测基准 |
| `cl100k_base`（GPT-3.5/4） | 1–3 tok | 汉字合并更少，压缩收益**更高** |
| Claude / Gemini | 未知 | 需实测，不能假设与 OpenAI 同构 |

`cangjie calibrate` 已经支持任意 `encoding`，产物按 `carriers-<encoding>.json` 分开存。
**建议**：把 `encoding` 写进 `.cangjie/config.json`，换模型时重新 calibrate 一次（40 秒）。

### 1.4 避免"载体撞车"的进阶做法

现在靠"扫一遍语料排除已出现的字符"。更稳的做法是**保留一个不可压缩前缀**：
所有字码前加一个零宽标记（U+2060），编码器识别它才解码。
代价是每次命中 +1 token，收益直接砍半——所以只建议在"混排人类可读内容"时开。

## 2. 挖掘层（收益最大，但难）

### 2.1 用模型自身做分词，而不是 n-gram

现在的边界判断靠邻接熵 + 凝聚度 + 虚词表，属于"统计式新词发现"，误判率约 20–30%。
更准的做法：**让模型对候选做一次"是否是一个术语"的二分类**（一次批量调用几千条，成本极低）。
或者用 `jieba`/`pkuseg` 之类的分词器做初筛，再用统计量复核。

### 2.2 用户种子词表（性价比最高的一条）

让用户给 5–20 个"这个项目最常说的词"，直接入库并锁定不淘汰。
理由：真正的领域术语（项目代号、模块名、内部黑话）恰恰是统计量最难挖到的——
它们可能只出现 2 次，但每次都很长。

```bash
cangjie seed --add "厄瑞玻斯" --add "曜岩日晷" --add "潮汐锁定"
```

### 2.3 变体归并

`数据库连接池` / `数据库连接池的` / `数据库连接池配置` 会被当成三条。
建议做**后缀树归并**：若 A 是 B 的前缀且 `count(B) > 0.5 × count(A)`，只保留 B 并把 A 的命中算给 B。

### 2.4 用"重读次数"给候选加权

现在 `net = freq × (cost − gcost) − entry`，所有人一视同仁。
但**每轮都读的文本**（系统提示、术语表）和**只读一次的文件**价值差 20 倍。
建议增加"来源权重"：`Z1/系统提示 = 5.0`，`最近文件 = 1.0`，`归档 = 0.2`。

## 3. 编码层（锦上添花）

### 3.1 位置感知码表

同一个字在高频区可以代表更常见的短语，但前提是解码器知道"当前位置属于哪个区段"。
实现方式是**分段码表**：在文本里插入极少量分区标记，每区独立查表。
收益约 +0.5%，复杂度显著上升——**不建议 v1.x 做**。

### 3.2 编解码的确定性

同一份字典 + 同一段文本，必须永远产出同一串字码（当前已满足）。
这条对 prompt caching 至关重要：**任何随机性都会让缓存失效**。

### 3.3 幂等压缩

对已压缩的文本再压一次，不应该再变化（`encode(encode(x)) == encode(x)`）。
现在天然满足（载体字不在短语索引里），但加了"两字码"之后要重新验证。

## 4. 上下文治理（真正的省钱开关）

### 4.1 工具输出裁剪模板（强烈建议内置）

90% 的 CLI 输出是噪音。给常见命令内置裁剪器：

| 命令 | 裁剪策略 |
|---|---|
| `pytest` / `jest` | 只留失败用例 + 末尾汇总 |
| `npm install` | 只留 error / warn / 包数量 |
| `git diff` | 只留变更统计 + 前 N 个 hunk |
| `ls -R` | 折叠为目录树 + 文件数 |
| `docker logs` | 只留 error 前后 5 行 |

数据：一次 `pytest` 全量输出 12k token，裁剪后 800 token（**-93%**）。
**这一条比字码强 20 倍，应该优先实现。**

### 4.2 增量摘要（别每次全量重写）

现在 `pack` 每次从头压全语料。更省的做法：
- Z2 归档保持不变；
- 每轮只把"最近 5 轮"追加压进 Z1 的尾部；
- Z1 超预算时，把最老的 30% 丢给模型做一次"折叠成 3 行结论"。

这是"滚动摘要"，能让 Z1 的重建成本从 O(全语料) 降到 O(5 轮)。

### 4.3 定点遗忘

长任务里通常只有 3–5 个"活变量"（当前 bug、当前目标、当前禁忌）。
建议维护一个结构化的 `state.json`（不是自然语言）：

```json
{"goal":"让检索延迟降到 200ms","blocker":"reranker OOM","decided":["改用 fp16","放弃缓存层"],"next":["跑基准"]}
```

这个文件 200 token，却顶替了 5000 token 的对话历史。

### 4.4 prompt caching 友好布局（容易踩坑，务必看）

```
[稳定前缀] 系统提示 + 密码本（只追加，不改动）   ← 缓存命中，1/10 价
[半稳定]   工作记忆包（每 5–8 轮变一次）        ← 部分命中
[变化]     最近 k 轮 + 本轮输入                  ← 全价
```

判断公式：`压缩收益 > 缓存未命中带来的差价`。
若 provider 缓存折扣是 90%，而你的压缩只有 4%，**每轮重建包反而亏**。
→ **包的重建频率必须低**，这是本 skill 最容易用错的地方。

## 5. 评估体系（现在完全缺失，最该补）

### 5.1 误码率

`decode(encode(x)) != x` 的比例。当前单元测试覆盖 4 类样本，但没跑过大规模真实语料。
建议：抽 1000 个真实文件做全量 roundtrip，任何一次失败都视为 P0 bug。

### 5.2 质量回归（关键，也是所有压缩方案的通病）

压缩后模型输出质量会下降吗？降多少？
建议做 **A/B 回放**：同一批问题，分别在原上下文 / 压缩上下文下跑，对比答案正确率。

我的预判：字码（无损，只换写法）对质量影响很小，风险在**模型不认识这些符号**，
导致注意力分配异常。需要实测验证，尤其是"一屏里出现 20 个 ▲△◆"时模型会不会混乱。

### 5.3 成本模拟器

`cangjie report` 里的 `simulate()` 是粗模型。建议接入真实计费：
`输入单价 × 缓存命中率 × 折扣 + 输出单价`，算出"这个项目用仓颉前后各花多少钱"。

## 7. 不要做的事（反面清单）

1. **不要压代码**。改坏一个标识符，调试成本远超省下的 token。
2. **不要压用户原话**。那是证据。
3. **不要追求高压缩率而降低 `min_gain`**。降到 1.0 以下，字典条目爆炸，净收益转负。
4. **不要用生僻汉字做载体**。实测 3 token/字，比被压的短语还贵（这是本项目最大的弯路）。
5. **不要每轮重建密码本**。缓存全失效，省 4% 赔 90%。
6. **不要在没有 A/B 数据时宣称"质量无损"**。只能说"文本无损"。
7. **不要跨模型复用同一份载体普查**。分词器不同，最优载体完全不同。

## 9. 最后一句实话

如果你的目标只是"别让上下文爆掉"，那么**裁剪 + 滚动摘要 + 结构化状态**三件套能解决 95% 的问题，
字码最多再挤 2–4 个百分点。

仓颉的价值不在"压得多"，在**"压了还能一字不差地还原，且专名一个都不丢"**。
在需要"长期记忆 + 可追溯"的场景里，这个性质比压缩率值钱得多。
